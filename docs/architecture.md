# Vosh architecture

The App section maps the Tauri app as far as the refactor has split it, with its commands and events, its lock order and two traces, one for a line you type and one for a line the game sends. Later refactor phases add which work runs on which thread, and each one moves the files the App section still lists.

This file describes the tree as it stands today. Part 2 of `docs/refactor-plan.md` holds the target, and each phase updates the section here that it changes.

## Crates

Vosh is one Cargo workspace. The Tauri app in `src-tauri` uses five library crates in `crates`. No crate knows about Tauri or the app, so each one builds and tests on its own. A `testkit` feature holds the items only tests call and keeps them out of the release build. The app's dev dependencies turn on the test kits of vosh-prompt, vosh-automation and vosh-log, and the vosh-automation tests turn on the one in vosh-protocol.

## App

`src-tauri` is vosh-app, the Tauri app. `src-tauri/src/lib.rs` holds the module list and `run()`, which builds the app with the macOS menu, the font scheme and the updater and window state plugins, and hands the rest to the app frame in `src-tauri/src/app/` and the command layer in `src-tauri/src/ipc/`. ### Commands and events

The page and the app reach each other by name, and each name is written once on each side.

- `handler()` in `src-tauri/src/ipc.rs` registers every command the page calls. The page calls a command by its Rust function name, so a command may move between files but keeps its name and its parameter names.
- `src-tauri/src/app/events.rs` names every event the app sends. Two names stay where the session builds them. Each GMCP package goes out as `session://gmcp/` and the package name, with its dots as dashes, and `test://frame` is a seam only tests hear.

### Lock order

`AppState` keeps its shared parts behind tokio mutexes. Two tasks that take the same two locks in opposite orders would each wait for the other for good, so the code keeps one order. Most steps take one lock, copy what they need and let go before they take the next. Where a step holds two at once, it takes them in this order.

1. The save lock, `PERSIST_LOCK` in `src-tauri/src/disk/save.rs`. It keeps two writes off one file. The saves hold it, and so do a profile switch from the save of the profile you leave through loading the next, the wizard, and the rename, copy and delete of a profile. Nothing waits for it while holding another lock. `#profile save` runs under the profile lock, so it only tries the save lock and says Vosh is saving when another write holds it. A line that may be `#profile reset` or `#profile load` reads global.toml under the save lock before it takes the profile lock.
2. The loadouts, `AppState::loadout_set`, and the plugin manager, `AppState::plugins`. Turning loadouts on or off holds them while it lays their groups over the profile, and launch holds the plugin manager while each plugin it loads runs against the profile.
3. The profile, `AppState::profile`. The session task, the commands that read or change the live profile and the saves take it.
4. The profile set, `AppState::profile_set`. The save in loadout mode reads the sharing scope from the set while it holds the profile. Every other step that needs both, such as a switch, the save in per profile mode and the detail Settings shows for a profile, reads the set and lets go of it before it locks the profile. A step that holds the set never waits for the profile.

Two pairs sit apart from these. The session slot, `AppState::session`, comes before every lock the session task takes. A disconnect, and a connect that finds another session in the slot, hold it while they wait for the old task to end, and that task locks the profile, the log and the scrollback as it ends. The log, `AppState::logs`, comes before the log reader, `AppState::log_reader`, which `#logs forget-passwords` holds while it rewrites the log so no search reads it halfway. The catalog, `AppState::global_catalog`, is only ever held alone. The std mutexes in `AppState`, such as the window size and the live connection, guard a quick copy and are never held across an await.

### A line you type

1. `submitLine` in `src/components/Input.tsx` plans the line with `planSubmit` from `src/lib/maskedInput.ts`. Your echo goes on screen at once through `writeLive` in `src/App.tsx`, which writes it to xterm and hands it to the native grid and the session with `terminal_local_write`. Then `sendInput` in `src/lib/session.ts` invokes `session_send_input`. A line from the masked password field goes straight to the session through `session_send_masked` instead, which skips the input pipeline, and the log keeps `> (hidden)` in its place.
2. `session_send_input` in `src-tauri/src/ipc/session.rs` takes the line and hands it to `run_typed_line` in `src-tauri/src/input.rs`. `#help` opens Help on the main window and `#logs` runs on a task of its own, and neither goes further. A line that may be `#profile reset` or `#profile load` reads global.toml first through `read_shared_layer` in `src-tauri/src/profile/switch.rs`. Then, under the profile lock, `run_line` in the same file runs the line. A slash command acts on the live profile. Target words and quick keys expand, then variables interpolate and aliases expand, and the Lua body of a script alias runs where it stands. `run_line` hands back the bytes for the game, the lines to echo and what the Lua asks for.
3. With the profile lock let go, `run_typed_line` repaints your prompt when a `#prompt` line changed how it looks, through `request_prompt_repaint` in `src-tauri/src/prompt.rs`. `settle_line_effects` in `src-tauri/src/disk/save.rs` sends the events a replace or a tick change owes and starts the save a slash command asks for, and `session://target` goes out when your target changed.
4. `deliver_script_result` applies what the Lua asked for through `collect_script_result` in `src-tauri/src/session/effects.rs`, prints the echo lines through `echo_lines`, and hands the bytes to the session task through `SessionHandle::send`. With no connection, the terminal prints `[not connected]`.
5. `io_loop` in `src-tauri/src/session/conn.rs` takes the bytes. A partial line still waiting for the next read shows first, and lines held for the rest of a prompt let go, since your line follows them. `send_step` records a prompt candidate and closes the open row. The bytes go to the socket, and the rows that record what you sent wait for the log, which writes them once the socket is quiet. While the game hides your input, each row reads `> (hidden)`.

### A line the game sends

1. `io_loop` reads the socket, and the telnet parser in `crates/protocol/src/telnet.rs` splits the bytes into text, commands and subnegotiations. `handle_event` takes each in order. A negotiation answer goes straight back to the socket. A GMCP packet goes to `handle_gmcp`. Under the profile lock it updates the variables and the values your prompt reads, and the Lua that listens for it runs. A character name then runs the auto switch in `src-tauri/src/profile/switch.rs`, and the packet goes to the page as `session://gmcp/` and its package name.
2. Text goes to the line accumulator in `src-tauri/src/line_accumulator.rs`, which hands back each complete line. `line_step` takes each line under the profile lock. The prompt stage in `crates/prompt/src/stage/` decides whether it is your prompt, a line of one or a plain line. A plain line runs the Line pass. Its triggers in `crates/automation/src/trigger.rs` match the plain text from `crates/protocol/src/ansi.rs` and highlight, gag, replace, send or route the line, the tick checks its reset pattern, and Lua triggers run. What the line shows lands in the read's batch, and its log row waits for the log.
3. With the profile lock let go, `deliver_line_step` sends a routed line to its panes as `session://routed`, keeps the line in the scrollback ring, writes what triggers send to the socket and applies what the Lua asked for.
4. At the end of the read, `end_read` hands the partial after the last line end to the stage, and `finish_read` sends the whole batch once, then the prompt events. One read is one write to the screen, so a prompt that arrives in one read never flashes.
5. `emit_counted` sends the batch to both renderers under `OUTPUT_ORDER`, so they take the output of every caller in the same order. The native grid takes it first, through `feed_session_output` in `src-tauri/src/term_grid.rs`, and the surface draws it on the frame the session asks for once the burst of reads ends. Then the page hears the same payload as `session://output`. `onOutput` in `src/components/Terminal.tsx` word wraps it with `OutputShaper` in `src/lib/outputShaper.ts` and writes it to xterm through `RegionWriter` in `src/lib/terminalRegion.ts`, the page side of two twins below. While the native grid shows, xterm only reads the text for tab completion.

## Twins

Two renderers draw the same terminal, xterm on the page and the native grid in Rust. So these jobs exist twice on purpose, and the refactor does not merge them. A change to one side lands on the other side in the same commit, and the Held by column names what keeps the two in step.

### Pairs kept by hand

Each of these is a value both sides need, and a test fails when the two drift. Where a Rust test reads a page file by its path, R16 moves the page file and that path in the same commit.

- The known worlds. `KNOWN_WORLDS` in `src-tauri/src/profile_set.rs` and in `src/lib/useConnection.ts`. A test in profile_set.rs reads the page's list.
