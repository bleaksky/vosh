# Vosh architecture

The App section maps the Tauri app as far as the refactor has split it, with its commands and events, its lock order and two traces, one for a line you type and one for a line the game sends. The Page section maps the folders of the page. Later refactor phases add which work runs on which thread, and each one moves the files the App section still lists.

This file describes the tree as it stands today. Part 2 of `docs/refactor-plan.md` holds the target, and each phase updates the section here that it changes.

## Crates

Vosh is one Cargo workspace. The Tauri app in `src-tauri` uses five library crates in `crates`. No crate knows about Tauri or the app, so each one builds and tests on its own. A `testkit` feature holds the items only tests call and keeps them out of the release build. The app's dev dependencies turn on the test kits of vosh-prompt, vosh-automation and vosh-log, and the vosh-automation tests turn on the one in vosh-protocol.

## App

`src-tauri` is vosh-app, the Tauri app. `src-tauri/src/lib.rs` holds the module list and `run()`, which builds the app with the macOS menu, the font scheme, the updater and window state plugins, the notification plugin on Windows and Linux and the single instance guard on Windows, and hands the rest to the app frame in `src-tauri/src/app/` and the command layer in `src-tauri/src/ipc/`. No code below the command layer calls a command, so a step that a command and the session both run, such as a profile switch, lives below it.

### Commands and events

The page and the app reach each other by name, and each name is written once on each side.

- `handler()` in `src-tauri/src/ipc.rs` registers every command the page calls. The page calls a command by its Rust function name, so a command may move between files but keeps its name and its parameter names.
- `src-tauri/src/app/events.rs` names every event the app sends. Two names stay where they are built. Each GMCP package goes out as `session://gmcp/` and the package name, with its dots as dashes, from `src-tauri/src/session/gmcp.rs`, and `test://frame` in `src-tauri/src/output.rs` is a seam only tests hear.
- `fixtures/ipc/names.txt` holds both, each command with the keys its function reads and each event with who sends it. The IPC contract test in `src-tauri/src/tests/ipc_contract.rs` holds the page and the app to it, and `VOSH_WRITE_IPC_NAMES=1` writes it again.
- A command that reads or changes one session, its connection, its terminal or its prompt engine, takes a last argument `session`, a `SessionId` from `src-tauri/src/sessions.rs`. The page may leave it out, and then the command acts on the selected session. names.txt marks each with `session?`. A command that reads or changes a profile's automation, tick settings, UI config, panes or loadouts takes a last argument `profile`, the name of that profile, and names.txt marks each with `profile?`. Without it the command acts on the profile the selected session plays. Settings names the profile it shows in each of these, which `src/settings/shownProfile.ts` keeps, the selected session's unless a page with unsaved edits holds the one it showed. `AppState::lock_named` in `src-tauri/src/app/state.rs` finds a named profile and refuses a name no session plays, while `tracked_affects_set` and `pane_layout_reset` rewrite the file of any other. `alert_presets_get` and `alert_presets_set` take it too, since the Presets page reads and saves the alert presets with the rest. `reconnect_get` and `reconnect_set` take none yet. The Scripts commands take `session?` as well, since each session runs a Lua engine of its own. `plugin_create` and `plugin_set_enabled` edit the `[plugins]` list of the profile that session plays, and `plugin_save`, `plugin_reload`, `plugin_install` and `plugin_remove` act on every session and take it only to return the list as that session sees it, whether its profile turns each plugin on and whether Vosh stopped one there.
- Seven commands in `src-tauri/src/ipc/session.rs` work on the sessions themselves. `session_open` opens a session after the others, on the profile it names or else the one the selected session plays, and returns its id. `session_select`, `session_rename`, `session_move`, `session_set_address` and `session_close` must name the session they act on. A rename with no name, or a blank one, clears the name, and closing the only session is an error. `sessions_list` returns each session in order as a row. Every window hears the rows again on `vosh://sessions-changed` after a step that changes what one shows. `src/stores/session/sessionsStore.ts` keeps them on the page, selects a session through `session_select`, names one through `session_rename`, moves one through `session_move` as you drag its row, and keeps the sessions the window opened, which get a terminal each. Each window keeps its own copy, so Settings and Help follow the selection, a rename, a login or a switch in a session behind as the main window does.
- Every event of the session's stream whose payload is an object names the session that sent it, in a `session` field beside the payload's own, through `Session::emit` in `src-tauri/src/sessions.rs`. `session://output` names it in `OutputPayload` itself, since that is the hot path. The GMCP packages, each the packet as the game sent it, `session://prompt-vars`, a map of values, and `vosh://affect-full-changed`, a map of fulls, carry `{session, data}` through `Session::emit_data`, since a `session` key among their own would read as one more field, value or affect. `onGmcpPackage`, `onPromptVars` and `subscribeAffectFullChanged` in `src/ipc` hand their listeners the data and the session, as `onHidden` and `onRouted` hand theirs the payload and the session, and `StatePayload` names the session among its fields. `vosh://session-identity-changed`, which is null with no connection, `vosh://profile-switched`, which is a name, and the native renderer's events, whose payloads are a pair, a count, a cursor name or null, keep their shape.
- The windows show the profile in front, the one the selected session plays. An event that carries one profile's settings or lists goes out only while that profile is in front, which `AppState::in_front` in `src-tauri/src/app/state.rs` decides, and a change from any session on it counts. A session on a profile behind tells the windows only through its row on `vosh://sessions-changed`. A selection that brings another profile to the front sends its settings and then `vosh://profile-switched`, as a switch does, through `show_selection` in `src-tauri/src/app/launch.rs`, and `vosh://session-identity-changed` speaks for the selected session alone.

The page side mirrors the app.

- `src/ipc` holds every app command the page calls and every event it hears or sends, one file per topic, named like the modules in `src-tauri/src/ipc`. So `src/ipc/session.ts` holds the page's calls into `src-tauri/src/ipc/session.rs`, and `src/ipc/nativeSurface.ts` the 18 `native_surface_` commands and the five events the surface sends. `src/ipc/promptDesign.ts` takes drawing and editing a design out of `src/ipc/prompt.ts`, and `src/ipc/theme.ts` takes the custom theme shape and the theme events out of `src/ipc/uiConfig.ts`, so each file stays under 800 lines. The theme helpers that call nothing in Rust sit in `src/theme/themes.ts`. The rest of the page reaches the app's commands and events only through these wrappers. The Tauri window API, `getCurrentWindow` with its focus, title, close and resize calls, stays with the windows that call it.
- `src/ipc/events.ts` names every event once, as a constant named by its path in upper snake case, the way `src-tauri/src/app/events.rs` names the events the app sends. So `session://prompt-vars` is `PROMPT_VARS` on both sides. The GMCP packages have no constant, since `onGmcpPackage` in `src/ipc/session.ts` builds each name from the package's, as the session does. The contract test holds both sides to that rule and every page listen and emit to a constant from events.ts, and it fails for any invoke, listen or emit in a page file outside `src/ipc`.
- Components hear events through `useTauriEvent` in `src/ipc/useTauriEvent.ts`, which takes a subscribe and a handler. The subscribe comes from `src/ipc`, from a lib function that wraps one, or from the window API, such as `onResized`. It subscribes once at mount, hands each payload to the handler of the newest render and unlistens at unmount, a subscription that resolves after unmount included. An event only one platform or renderer sends, such as the macOS menu bar or the native surface click, goes through it with a subscribe that resolves to nothing elsewhere. An effect still subscribes by hand where it subscribes only while your prompt line shows or while it has a list, subscribes again when an input changes, takes no handler, or shares its cleanup with more work.
- `setUiFields` in `src/ipc/uiConfig.ts` saves the fields a page names through `ui_set_fields`, which writes only those and sends no event. `src/ipc/uiConfigBroadcast.ts` holds `broadcastUiConfigChanges`, which tells the other windows what one save changed, an event for each field or group of fields that moved, judged against the window's copy before the edit. The Settings writer in `src/settings/useSettingsAutoSave.ts` sends each save to the profile it was made on, and then its broadcast while that profile is in front. While a save waits or is on its way, the writer holds its fields, and Settings keeps its own value of a held field over a broadcast that comes back. `THEME_PREFS_FIELDS` in `src/ipc/theme.ts` names the four theme fields and `AFFECTS_DISPLAY_FIELDS` in `src/ipc/affects.ts` the five affects display fields, so `ThemePrefs`, `AffectsDisplayFields` and the check of what a save holds read one list each. `followReplacedUiConfig` sits beside the broadcast and follows a config the backend replaced.
- `src/theme/theme.ts` reads the config through `getUiConfig` in `src/ipc/uiConfig.ts`, which loads nothing that imports `src/theme/theme.ts`. `src/ipc/uiConfigBroadcast.ts` is the one config file that imports `src/theme/theme.ts`, so that file and the config files never form an import loop.

### Lock order

`AppState` and each session keep most of their shared parts behind tokio mutexes, and the session map and each connection behind std mutexes. Two tasks that take the same two locks in opposite orders would each wait for the other for good, so the code keeps one order. Most steps take one lock, copy what they need and let go before they take the next. Where a step holds two at once, it takes them in this order.

1. A session's slot, `Session::slot` in `src-tauri/src/sessions.rs`, which holds the handle to the task that runs its connection. `disconnect`, which `session_close` runs too, and a `connect` that finds another task in the slot, both in `src-tauri/src/session.rs`, hold it while they wait for the old task to end. Until it ends, that task may take any lock below. A login switch takes the save lock and the session map, and as it ends the task locks its profile, its connection, the log, the scrollback and the save lock. So no step takes a slot while it holds any of them. `prompt_config_set` in `src-tauri/src/ipc/prompt.rs` works out its change under the profile and the connection, lets go, and only then asks the session to repaint your prompt, and a test there pins it. It hands the change to the other sessions on the profile after it lets go too, and each one whose prompt the change redraws repaints from a task of its own.
2. The save lock, `PERSIST_LOCK` in `src-tauri/src/disk/save.rs`. It keeps two writes off one file. The saves hold it, and so do a profile switch from the save of the profile you leave through loading the next, the wizard, the rename, copy and delete of a profile, and each save of the session list to profiles.toml, which reads the sessions from the session map and lets go of it before it takes the profile set. Nothing but a slot holder, as above, waits for it while it holds another lock. `#profile save` runs under the profile lock, so it only tries the save lock and says Vosh is saving when another write holds it. A line that may be `#profile reset` or `#profile load` reads global.toml under the save lock before it takes the profile lock.
3. The turn of `broadcast_sessions` in `src-tauri/src/sessions.rs`, a std mutex that lets one broadcast of the session rows run at a time, so the newest rows always go out last. A caller may hold the save lock, and never a profile or a connection. Under the turn the broadcast takes the session map to list the sessions and lets go of it, then reads each row, which takes that session's leaf locks and then its connection lock, one session at a time. It blocks its thread on each connection lock while it holds the turn, so a session task that keeps its connection through a long step holds up every broadcast behind it.
4. The session map, `AppState::sessions` in `src-tauri/src/app/state.rs`, which lists the sessions of `src-tauri/src/sessions.rs` in order with the one selected, beside the profiles they play. It is a std mutex, held only to find, add or remove a session or an open profile or to read or change the selection. No holder awaits, and none takes another lock but the leaf locks below and one more. A change of selection shows the grid of the session it selects, so it takes the native grid map and then the pointer's state, in the native order below. A switch takes it under the save lock to count the sessions on the profile it leaves and to find, add and close the profiles it moves between, and `session_open`, `session_close` and the first selection of a session launch restored take it under the save lock too. So every step that opens or closes a session or moves one to another profile holds the save lock, and a switch that finds its session the last on a profile can save that profile and close it. `session_close` takes the session out of the map under the save lock and lets go of both, then ends its connection through the slot as Disconnect does, and only then takes the save lock again and its profile. A switch and the first selection of a restored session check under the save lock that the map still holds their session, and a connect checks it under the slot before it keeps its connection, so one that lands in that wait leaves no profile open and no connection running behind the close. Every step finds its session in the map before it takes any lock below the map, so no step takes the map while it holds the loadouts, a profile, the profile set or a connection. A command takes the session it names, or the selected one, through `AppState::session`, and the session loop keeps its own `Session` in its `Conn`. An alert rings once its step let go of the profile and the connection, so the focus rule reads the selection from the map with no lock held. The end of a connection reads the other sessions from the map before it locks one connection of theirs at a time, to learn whether one took the character, and so does a login that takes a character another session plays.
5. The loadouts, `AppState::loadout_set`. Turning loadouts on or off holds them while it lays their groups over the profile, and so do the group switches in Settings.
6. The profiles the sessions play, each an `OpenProfile` in `src-tauri/src/profile/open.rs` that the session map keeps, taken one at a time. The session task, the commands that read or change a profile and the saves take one. A step reaches the profile of its session through `Session::lock_profile`, which locks the profile the session points at, then checks the session still points at it, and takes the next one when a switch moved the session meanwhile. Two steps hold two profiles, the one that opened first first. A switch takes the profile it leaves and the next, then the session's connection, and moves the session under them, so a step of that session finds one or the other, whole. The first selection of a session launch restored moves it the same way from the defaults it waited on to its profile. A save that wrote global.toml or changed the catalog lets go of its profile, then locks each other open profile in turn to lay over it what it wrote. Under a profile, and under the session map, a holder may take two leaf locks, held for a copy, the profile pointer of a session, `Session::profile`, and the name of an open profile.
7. The profile set, `AppState::profile_set`. The save in loadout mode reads the sharing scope from the set while it holds the profile. Every other step that needs both, such as a switch, the save in per profile mode and the detail Settings shows for a profile, reads the set and lets go of it before it locks the profile. A step that holds the set never waits for the profile.
8. A session's connection, `Session::connection` in `src-tauri/src/session/connection.rs`, which holds your target, the room list, the room look, the fight's tail, the tick's count, the prompt engine, the session variables and the session's Lua engine, with the aliases and panes its plugins make and the macro recorder. It is taken after the profile and the profile set, and never before them. The session task takes it after the profile lock for each step that needs both, and alone for a step that needs only the connection, such as a send, a local write or a held partial. Every line the input pipeline runs, a prompt command that writes the `[prompt]` table or reads the profile too, a profile switch, `#profile load` and `#profile reset`, launch and the plugins it loads, the Settings tick save, the switch on a group heading in Settings and an import take it after the profile too. A command that needs only the connection, such as `target_get` and the prompt commands that read only the engine, takes it alone, so it never waits for the loop to answer. A step that reaches the other sessions on a profile reads them from the session map before it takes the profile, then under the profile takes the connection of each one that still plays it in turn, never two at once, through `ProfileGuard::players` in `src-tauri/src/profile/open.rs`. Its own connection is let go first or taken after. Those steps are the tick change a `#tick` line or the Settings tick save makes, which every other session on the profile follows through `follow_in_other_sessions` in `src-tauri/src/tick.rs`, what you choose in the `[prompt]` table with a `#prompt` or `#unprompt` line, `prompt_config_set` or `prompt_card_open`, which every other engine on the profile takes through `choose_in_other_sessions` in `src-tauri/src/prompt.rs`, a `#profile reset` or `#profile load`, whose tick settings and `[prompt]` table every other session on the profile takes through `hand_to_other_sessions` in `src-tauri/src/input/profile.rs`, each printing its line once the profile lets go, and a connect or a switch, which turns your tick on, or keeps it on, only when no other session on the profile it lands on is connected. It is a std mutex, `SharedConnection`, since the session task takes it for every line the game sends and an async take there cost P2 about 3 percent. No holder awaits, and the compiler holds every task to that, since the guard cannot cross an await. Under it a holder takes only leaf locks, the Lua limits mutex in the script crate for each Lua run, `UNREAD_FILES` in `src-tauri/src/disk/atomic.rs` for `#profile save` and `#profile load`, and a try of `PERSIST_LOCK` for `#profile save`. The price is that a waiter blocks its runtime thread instead of yielding until the holder lets go, and a holder can keep it a while. A line the game sends keeps it through its triggers and its Lua, each Lua call within its time budget. A line you type keeps it through the whole input pipeline, so `#profile save` writes the profile file and its backups under it, `#profile load` reads and parses one, and `#script load` and `#script reload` read scripts. A profile switch keeps it while it reads each plugin the next profile turns on and runs its entry script, one Lua budget per plugin in a row. A command such as `target_get` that comes in the middle waits on its thread through all of it, so on a machine with few cores a switch with plugins can hold up the other tasks until it ends. Each session holds its own, which outlives each connection the session makes.

The log, `AppState::logs`, comes before the log reader, `AppState::log_reader`, which `#logs forget-passwords` holds while it rewrites the log so no search reads it halfway. The catalog, `AppState::global_catalog`, and the plugin manager, `AppState::plugins`, are only ever held alone. A Scripts command holds the manager while it lists the plugins folder or while Install or Remove changes it, and lets go before it locks a profile. The other std mutexes in `AppState` and `Session`, such as a session's name, where it dials, its window size, the host and port of its live connection, the cap of its alerts and its series of redials, and the windows that have focus, guard a quick copy and are never held across an await. Their switches and counters are atomics, so no step waits on them.

The native renderer keeps an order of its own, of std mutexes outside `AppState`. A frame runs on the main thread. It holds the surface slot, `SURFACE` in `src-tauri/src/native/surface.rs`, then the grid map, `GRIDS` in `src-tauri/src/native/grid.rs`, which holds each session's grid with its find, and with both held it reads the hovered link in `src-tauri/src/native/surface/pointer.rs` and the style statics in `src-tauri/src/native/gpu/style.rs`, one at a time. Under the surface slot a frame also takes the session map, to find the selected session for the size it reports. `Sessions::select` in `src-tauri/src/sessions.rs` takes the grid map under the session map to show the grid of the session it selects, and then the pointer's state, to let go of a drag on the grid that showed before. So the order runs surface slot, session map, grid map, then the pointer's state and the style statics. Nothing that holds a lock later in that order takes an earlier one. `emit_counted` in `src-tauri/src/output.rs` feeds a grid under `OUTPUT_ORDER`, which no frame takes. `src-tauri/src/native.rs` gives the same order at its top.

### A line you type

1. `submitLine` in `src/input/Input.tsx` plans the line with `planSubmit` from `src/input/maskedInput.ts`. Your echo goes on screen at once through `writeTo` in `src/shell/useSessionTerminals.ts`, which writes it to the xterm of the session the command line belongs to and hands it to the native grid and the session with `terminal_local_write`. Then `sendInput` in `src/ipc/session.ts` invokes `session_send_input` with that session, so a line goes where you typed it even when the selection moves before it lands. A line from the masked password field goes straight to the session through `session_send_masked` instead, which skips the input pipeline, and the log keeps `> (hidden)` in its place.
2. `session_send_input` in `src-tauri/src/ipc/session.rs` takes the line and hands it to `run_typed_line` in `src-tauri/src/input.rs`, which runs it in the session the command names, or the selected one. `#help` opens Help on the main window and `#logs` runs on a task of its own, and neither goes further. A line that may be `#profile reset` or `#profile load` reads global.toml first through `read_shared_layer` in `src-tauri/src/profile/switch.rs`. Then, under the profile lock and then the connection lock, `run_lines_locked` in `src-tauri/src/session/effects.rs`, which runs a line from a timer, the tick or Lua too, hands the line to `run_line` in `src-tauri/src/input.rs`. A slash command goes through `handle_slash` in `src-tauri/src/input/slash.rs` to the file of its topic and acts on the live profile and the connection. The target words run in `src-tauri/src/input/target.rs` and a quick key expands, then variables interpolate and aliases expand, and the Lua body of a script alias runs where it stands. `run_line` hands back the bytes for the game, the lines to echo and what the Lua asks for.
3. With both locks let go, `run_typed_line` repaints your prompt when a `#prompt` line changed how it looks, through `request_prompt_repaint` in `src-tauri/src/prompt.rs`. `settle_line_effects` in `src-tauri/src/disk/save.rs` sends the events a replace or a tick change owes, brings every other session on the profile to a tick change and to what a `#prompt` line chose, hands them what a `#profile reset` or `#profile load` laid over the profile with a line that names your session, and starts the save a slash command asks for, and `session://target` goes out when your target changed.
4. `deliver_script_result` in `src-tauri/src/input.rs` applies what the Lua asked for through `collect_script_result` in `src-tauri/src/session/effects.rs`, prints the echo lines in the session through `echo_lines` in `src-tauri/src/output.rs`, and hands the bytes to the session task through `SessionHandle::send` in the session's slot. With no connection, the terminal prints `[not connected]`.
5. `io_loop` in `src-tauri/src/session/conn.rs` takes the bytes. A partial line still waiting for the next read shows first, and lines held for the rest of a prompt let go, since your line follows them. `send_step` in `src-tauri/src/session/steps.rs`, under the connection lock alone, records a prompt candidate and closes the open row. The bytes go to the socket through the stream the `Conn` holds, and the rows that record what you sent wait in the burst's `Settle` from `src-tauri/src/session/batch.rs` for the log, which writes them once the socket is quiet. While the game hides your input, `ServerEcho` in `src-tauri/src/session/echo.rs` makes each row read `> (hidden)`.

### A line the game sends

1. Each session runs its own `io_loop` in `src-tauri/src/session/conn.rs`, which keeps the `Session` in its `Conn`. It reads the socket and hands the bytes to `Conn::handle_read` in `src-tauri/src/session/read.rs`, the one read path, which the drain after a read error takes too. The telnet parser in `crates/protocol/src/telnet.rs` splits the bytes into text, commands and subnegotiations, and `handle_event` takes each in order. A negotiation answer goes straight back to the socket. A GMCP packet goes to `handle_gmcp` in `src-tauri/src/session/gmcp.rs`. Under the lock of the profile the session plays, through `Session::lock_profile`, and then its connection lock, it updates the session's variables, the room list and the values your prompt reads, and the Lua in the session's engine that listens for it runs. A new character name then runs the auto switch in `src-tauri/src/profile/switch.rs`, which moves this session alone, and the packet goes to the page as `session://gmcp/` and its package name.
2. Text goes to the line accumulator in `src-tauri/src/session/lines.rs`, which hands back each complete line. `line_step` in `src-tauri/src/session/steps.rs` takes each line under the same two locks. The prompt stage in `crates/prompt/src/stage/` decides whether it is your prompt, a line of one or a plain line. A plain line runs the Line pass. The profile's triggers in `crates/automation/src/trigger.rs`, less those whose Lua this session stopped, match the plain text from `crates/protocol/src/ansi.rs` and highlight, gag, replace, send or route the line, the tick checks its reset pattern, and Lua triggers run. What the line shows lands in the read's batch, the `ReadBatch` from `src-tauri/src/session/batch.rs`, and its log row waits for the log.
3. With both locks let go, `deliver_line_step` in `src-tauri/src/session/read.rs` sends a routed line to its panes as `session://routed`, keeps the line in the scrollback ring, writes what triggers send to the socket and applies what the Lua asked for.
4. At the end of the read, `end_read` hands the partial after the last line end to the stage, and `finish_read` sends the whole batch once, then the prompt events. One read is one write to the screen, so a prompt that arrives in one read never flashes.
5. `emit_counted` in `src-tauri/src/output.rs` sends the batch to both renderers under `OUTPUT_ORDER`, so they take the output of every caller in the same order. The session's native grid takes it first, through `feed_session_output` in `src-tauri/src/native/grid.rs`, which writes its regions through `src-tauri/src/native/grid/regions.rs`, and while that grid shows, the surface draws it on the frame the session asks for once the burst of reads ends. Then the page hears the same payload as `session://output`, with the session named in it. The main window keeps a terminal for each session it opened, and only the selected session's shows. The handler `src/terminal/Terminal.tsx` passes to `onOutput` from `src/ipc/terminal.ts` takes only its own session's output, word wraps it with `OutputShaper` in `src/terminal/outputShaper.ts` and writes it to xterm through `RegionWriter` in `src/terminal/terminalRegion.ts`, the page side of two twins below. While the native grid shows, xterm only reads the text for tab completion.
